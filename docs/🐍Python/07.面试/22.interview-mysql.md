## 一、基础与存储引擎

### Q1　InnoDB 和 MyISAM 怎么选？为什么默认是 InnoDB？　🔥🔥

**答题要点**

选 InnoDB。InnoDB 支持**事务、行级锁、崩溃恢复（Redo Log）、外键、MVCC 非阻塞读**；MyISAM 只有表级锁、没有事务、崩溃后可能损坏。MyISAM 唯一残留优势是 `COUNT(*)` 为 O(1)（存储了行数），但现代业务不值得为它牺牲事务和并发能力。

**追问方向**

- 「InnoDB 的内存/磁盘结构？」——内存：Buffer Pool 管理数据页，默认页 16KB；磁盘：表空间、Redo Log、Undo Log。
- 「MyISAM 支持全文检索吗？」——5.6 起 InnoDB 也支持，不再是 MyISAM 的独有优势。

### Q2　CHAR、VARCHAR、TEXT 的区别　🔥

**答题要点**

| 类型 | 特点 | 适用 |
|---|---|---|
| `CHAR(n)` | 定长，不足补空格 | 定长值：国家代码、MD5 |
| `VARCHAR(n)` | 变长，1–2 字节长度前缀，`n` 计入 65535 字节行限制 | 绝大多数场景 |
| `TEXT` | 大文本，可 off-page 存储，**只能前缀索引** | 确实超过 VARCHAR 合理范围时 |

**追问**：VARCHAR(255) 为什么常见？——早期 MySQL 用 1 字节存长度（上限 255），且足够容纳大多数短文本；UTF-8 下 255 字符最多 765 字节，仍远小于行限制。

### Q3　自增主键 vs UUID 主键　🔥🔥

**答题要点**

InnoDB 用主键组织聚簇索引。**自增主键顺序写入**，不频繁页分裂；UUID 随机写入导致页分裂和碎片，且二级索引叶子存主键值，UUID 更长→浪费空间。

**追问**：没有主键会怎样？——InnoDB 选第一个唯一非空索引；都没有则隐式生成 6 字节 ROWID。

### Q4　三大范式与反范式　🔥

**答题要点**

1NF 列不可再分；2NF 消除非主属性对候选键的部分依赖；3NF 消除传递依赖。

实际设计常**故意反范式**：订单表冗余用户姓名避免联表查询，用冗余换性能，代价是一致性维护成本。

## 二、索引（追问链条最长的一块）

### Q5　为什么是 B+树，不是 B 树 / 红黑树 / Hash？　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 核心就一句话：索引的目标是减少磁盘 IO，B+树把这个指标压到最低。
>
> 先说和 B 树比。B+树的非叶子节点**只存键和指针、不存数据**，所以一个 16KB 的页能装下更多键，树高通常只有 3 到 4 层，查千万级数据也就三四次磁盘 IO；而且叶子节点用双向链表串起来，范围查询和排序只要沿链表顺序扫，B 树得做中序遍历，麻烦得多。
>
> 再说红黑树。它是二叉树，高度随数据量涨，百万级数据就有约 20 层，20 次磁盘 IO 完全不能接受，而且它不支持范围扫描。Hash 更直接——只支持等值查询，范围、排序、模糊统统不行。至于 InnoDB 的 Adaptive Hash Index，那是引擎内部的自适应优化，不是我们能选的索引结构。
>
> 所以记住三个数：B+树 3–4 层、每层一次磁盘 IO、InnoDB 页默认 16KB。答到"非叶子不存数据导致树矮、IO 少"，这题的骨架就立住了。

**答题骨架**

- **vs B 树**：非叶子只存键和指针，单页容纳更多键→树高 3–4 层承载千万级；叶子双向链表，范围/排序高效。
- **vs 红黑树**：二叉高度随数据量线性上升（百万级约 20 层），磁盘 IO 不可接受，不支持范围扫描。
- **vs Hash**：只支持等值，不支持范围、排序、模糊；Adaptive Hash Index 是内部优化，非用户可选。

**必备数字**：B+树 3–4 层，每层一次磁盘 IO；InnoDB 页默认 16KB。

### Q6　聚簇索引 vs 二级索引，什么是回表？　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 这题我会先把两种索引的"叶子存什么"讲清楚，回表就是它的自然推论。
>
> 聚簇索引的叶子节点存**完整数据行**，一张表只有一个，InnoDB 里就是主键索引。二级索引的叶子节点只存**索引键 + 主键值**。所以当查的列不全在二级索引里时，数据库先查二级索引拿到主键，再拿主键回聚簇索引查一次完整行——这就是回表，多一次 IO。
>
> 怎么避免回表？用**覆盖索引**：查询需要的所有列都在索引里，就不用回表，`EXPLAIN` 的 Extra 会显示 `Using index`。比如经常按 age 查 name，就建 `(age, name)` 联合索引。
>
> 顺着这个还能讲两个延伸：为什么主键推荐自增短类型？因为二级索引叶子都要存主键，主键越长越费空间；为什么更新主键代价大？因为二级索引都引用它，得一起改。

**答题骨架**

- **聚簇索引**：叶子存完整数据行，一表一个，InnoDB 中即主键索引。
- **二级索引**：叶子存「索引键 + 主键值」，查非索引列需回表。
- **覆盖索引**：查询列全在索引中，无需回表，`EXPLAIN` Extra 显示 `Using index`。

### Q7　最左前缀原则与联合索引　🔥🔥

**答题要点**

联合索引 `(a,b,c)` 从左到右匹配，**遇到范围查询停止**：

- `WHERE a=1 AND b>2 AND c=3` → 只用到 `a` 和 `b`，`c` 用不上。
- `WHERE b=1 AND c=2` → 完全用不上该索引。
- `WHERE a=1 AND c=3` → 用到 `a`，`c` 不能直接定位（但可能走覆盖索引扫描）。

**追问**：联合索引顺序怎么定？——区分度高的列放前面，同时兼顾常用查询条件。

### Q8　索引失效的常见场景　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 我会先列场景，最后补一句关键的话——是否失效最终由优化器基于统计信息决定，`EXPLAIN` 才是判断依据，别把"失效"说成绝对。
>
> 常见场景有六类。第一，违反最左前缀，联合索引跳过了最左列。第二，索引列上做函数或表达式，比如 `DATE(create_time)`，索引存的是原值，匹配不上。第三，隐式类型转换，字符串列传数字、数字列传字符串，MySQL 会偷偷转换导致索引失效。第四，`LIKE '%xxx'` 左通配，前缀不确定没法用 B+树定位。第五，`OR` 连接了非索引列，一边没索引就得全表扫。第六，负向查询 `NOT IN`、`!=`，取决于数据分布，如果优化器判断回表代价比全表扫还高，就干脆不用索引。
>
> 最后那句一定要说：这些不是铁律，是"大概率失效"，具体得看优化器的成本估算，`EXPLAIN` 看 type 和 key 才算数。

**答题骨架**

① 违反最左前缀；② 索引列做函数/表达式；③ 隐式类型转换；④ `LIKE '%xxx'` 左通配；⑤ `OR` 连接非索引列；⑥ 负向查询（`NOT IN`/`!=`，取决于数据分布）；⑦ 优化器判断全表扫描更快。

> **答题技巧**：不要只列场景，补一句"是否失效最终由优化器基于统计信息决定，`EXPLAIN` 是判断依据"。

## 三、事务、隔离级别与 MVCC

### Q9　ACID 分别靠什么实现？　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 这题我会把四个字母逐个对应到实现机制，这样比干背定义好记。
>
> 原子性 A 靠 **Undo Log**——事务回滚时用它把未提交的修改撤销。持久性 D 靠 **Redo Log**——提交后即使崩溃，也能靠 Redo 恢复。隔离性 I 靠**隔离级别 + MVCC + 锁**三者配合，MVCC 负责非阻塞的一致性读，锁负责写冲突。一致性 C 比较特殊，它不是一个单独机制，而是**业务逻辑 + 数据库约束**共同保证的结果，前三个 ACI 都是为它服务的。
>
> 所以一句话记法：A 靠 Undo，D 靠 Redo，I 靠锁和 MVCC，C 是前面三个加上业务约束共同达成的目标。

**答题骨架**

- **原子性**：Undo Log，回滚未提交的修改。
- **持久性**：Redo Log，提交后崩溃可恢复。
- **隔离性**：隔离级别 + MVCC + 锁。
- **一致性**：业务逻辑 + 数据库约束共同保证，非单一机制。

### Q10　四种隔离级别与三种读问题　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 我先给表格，再主动回答那个必追的坑——RR 到底有没有解决幻读。
>
> 四个级别从低到高：读未提交 RU 三种问题都有；读已提交 RC 避免脏读，但有不可重复读和幻读；可重复读 RR 是 InnoDB 默认，避免脏读和不可重复读，幻读基本避免；串行化全避免但并发最低。记的时候抓住每一级"新增避免了什么"：RC 比 RU 多了不脏读，RR 比 RC 多了可重复读。
>
> 关键的坑：RR 真的完全解决幻读了吗？严格说没有完全。快照读靠 MVCC 看到的是历史版本，能避免部分幻读；当前读靠临键锁锁住间隙、阻止插入，也能防。但如果你先做一次快照读、再做一次当前读同一个范围，当前读会看到最新数据，就可能看到"幻影"。所以更稳的说法是：RR 对幻读的防护**依赖于读方式**，快照读和当前读混用时仍有边界情况——承认这一点比硬说"完全解决"更专业。

**答题骨架**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 避免 | 可能 | 可能 |
| REPEATABLE READ（InnoDB 默认） | 避免 | 避免 | 基本避免（间隙锁） |
| SERIALIZABLE | 避免 | 避免 | 避免 |

> **追问：RR 真的完全解决幻读了吗？** 快照读靠 MVCC 避免部分幻读；当前读靠临键锁防插入；但先快照读、再当前读同一范围，仍可能看到"幻影"——严格说 RR 的幻读防护依赖读方式。

### Q11　MVCC 的实现原理　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> MVCC 就三个支柱：隐藏字段、Undo Log 版本链、ReadView。我把它们串成一条线讲。
>
> 每行记录有隐藏字段，关键是 `DB_TRX_ID`——最后修改这行的事务 ID，还有 `DB_ROLL_PTR`——指向 Undo Log 里的旧版本。更新一行时 InnoDB 不覆盖原数据，而是把旧版本放进 Undo Log，用 roll pointer 串成一条版本链。
>
> 那么一个事务来读的时候，该看版本链上的哪一版？靠 ReadView 判断可见性。ReadView 记录了当前活跃的事务列表，拿版本链上每版的 `DB_TRX_ID` 去比对，决定这一版对当前事务可不可见，不可见就顺着链往前找。
>
> 最后一个必答的延伸：RC 和 RR 在 MVCC 上最大的区别是什么？是 **ReadView 生成时机**——RC 每条 SELECT 都生成新的 ReadView，所以能看到别人新提交的；RR 只在事务首次 SELECT 时生成一次然后复用，所以整个事务看到的是同一份快照，这就是可重复读的由来。

**答题骨架**

三个支柱：**隐藏字段 + Undo Log 版本链 + ReadView**。

- 每行有 `DB_TRX_ID`（最后修改的事务 ID）和 `DB_ROLL_PTR`（指向 Undo Log 旧版本）。
- 更新不覆盖原数据，旧版本在 Undo Log 中串成版本链。
- **ReadView** 判断可见性：RC 每次 SELECT 生成新 ReadView；RR 首次 SELECT 生成后复用，实现可重复读。

**追问**：RC 和 RR 在 MVCC 上最大的区别？——ReadView 生成时机不同：RC 每条语句生成，RR 事务级复用。

### Q12　快照读 vs 当前读　🔥🔥

**答题骨架**

- **快照读**：普通 `SELECT`，读 Undo Log 中的历史版本，不加锁。
- **当前读**：`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`INSERT/UPDATE/DELETE`，读最新版本并加锁。

> 这是理解 Q10 幻读防护和 Q14 间隙锁的前提——锁只在当前读下生效。

## 四、锁与死锁

### Q13　InnoDB 的锁分类　🔥🔥

**答题骨架**

- 按粒度：表锁、行锁。
- 按模式：共享锁（S）、排他锁（X）。
- **按算法（InnoDB 核心）**：记录锁（Record Lock）、间隙锁（Gap Lock）、临键锁（Next-Key Lock）。
- 辅助锁：意向锁（IS/IX）、MDL（元数据锁）、AUTO-INC 锁。

### Q14　间隙锁与临键锁解决了什么？RC 和 RR 下有什么区别？　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 先讲间隙锁锁的是什么：它锁的是索引记录之间的"空隙"，目的很明确——阻止别的事务往这个空隙里插数据。间隙锁加上记录锁，合起来就是临键锁，这是 InnoDB 在 RR 下防止幻读的核心手段，因为幻读的本质就是"我查的时候没有，你却往这个范围插了新的"。
>
> 然后讲 RC 和 RR 的关键区别，这是拉开差距的地方：**间隙锁基本只在 RR 下生效**，RC 下间隙锁基本被禁用，只保留外键检查和唯一性检查需要的那一点。为什么？因为 RC 允许不可重复读和幻读，不需要靠间隙锁去防。
>
> 由此能推出一个工程结论：RC 的并发更高、死锁概率更低，代价是接受幻读可能。所以高并发写入场景，评估 RC 加业务幂等，往往比盲目依赖 RR 更划算。

**答题骨架**

- **间隙锁**锁住索引记录间的"间隙"，阻止插入；配合记录锁形成**临键锁**，用于 RR 下防幻读。
- **RC 下间隙锁基本不生效**（只留外键/唯一性检查所需），因此 RC 并发更高、死锁概率更低，但接受幻读可能。

### Q15　行锁什么时候会"降级"为表锁？　🔥🔥

**答题要点**

当 `UPDATE/DELETE` 的 `WHERE` 条件**没走索引**时，InnoDB 无法定位具体行，会锁住扫描到的所有行甚至整张表（实际是锁住所有扫描到的索引记录，效果接近表锁）。

> 核心原则：**行锁依赖索引**。这也是 Q16 死锁排查和 Q17 慢 SQL 优化的隐藏考点。

### Q16　死锁：四个条件、排查、避免　🔥🔥

**答题骨架**

- **必要条件**：互斥、持有并等待、不可剥夺、循环等待。
- **排查**：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`；开 `innodb_print_all_deadlocks` 写错误日志。
- **避免**：按固定顺序访问资源、缩短事务、控制事务粒度、为条件列建索引减少锁范围、必要时降级到 RC。

**加分回答**：间隙锁在 RR 下容易产生"插入意向锁等待"型死锁；高并发写入可评估 RC + 业务幂等，而非盲目依赖 RR。

## 五、SQL 优化与执行计划

### Q17　一条 SQL 很慢，你的完整排查流程　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 我按四步走：定位、分析、优化、验证，不会上来就说"加索引"。
>
> 第一步定位，从慢查询日志入手，用 `mysqldumpslow` 或 `pt-query-digest` 找出 Top SQL——先确认到底是哪条慢、慢在什么场景，别凭感觉。
>
> 第二步分析，用 `EXPLAIN` 看四个字段：`type` 看访问类型有没有到 range/ref，`key` 看实际用了哪个索引，`rows` 看扫描行数，`Extra` 看有没有 `Using filesort`、`Using temporary` 这种危险信号。
>
> 第三步优化，分四个层次：索引优化、SQL 改写、表结构调整、数据量太大就做分批或异步。不是所有慢 SQL 都靠加索引，有时候是返回字段太多、或者深分页，得对症下药。
>
> 第四步验证，优化前后对比执行计划和实际耗时，确认真的变快了、而且没引入新问题。这四步走完，回答就完整了。

**答题骨架**

① **定位**：慢查询日志 + `mysqldumpslow` / `pt-query-digest` 找 Top SQL；② **分析**：`EXPLAIN` 看 `type`、`key`、`rows`、`Extra`；③ **优化**：索引、SQL 改写、表结构、分批/异步；④ **验证**：对比优化前后执行计划与实际耗时。

### Q18　EXPLAIN 关键字段怎么看　🔥🔥🔥

**答题骨架**

| 字段 | 关注点 |
|---|---|
| **type** | 性能从优到劣：`system > const > eq_ref > ref > range > index > ALL`。至少到 `range`，最好 `ref` |
| **key** | 实际使用的索引；**key_len** 判断联合索引用了哪几列 |
| **Extra** | `Using index`（覆盖索引，好）；`Using filesort`、`Using temporary`（需关注） |

> 面试常被追问："`type=index` 和 `type=ALL` 区别？"——都扫全表，但 index 扫的是索引树（通常更小），ALL 扫的是数据行。

### Q19　深分页为什么慢？怎么优化？　🔥🔥

**答题要点**

`LIMIT 10000000, 10` 需要扫描并丢弃前 1000 万行。优化：

1. **游标分页**：`WHERE id > last_id ORDER BY id LIMIT 10`——用上一页最大 id 做锚点。
2. **延迟关联**：先用覆盖索引查出主键，再回表取完整行，减少回表次数。

### Q20　JOIN 的三种算法　🔥

**答题骨架**

- **NLJ（Nested-Loop Join）**：驱动表每行去被驱动表走索引，有索引时最优。
- **BNL（Block Nested-Loop）**：被驱动表无索引时用 join buffer 批量匹配，仍较慢。
- **Hash Join**（8.0.18+）：无索引大表等值连接时构建哈希表，复杂度接近 O(N+M)，通常远快于 BNL。

## 六、日志与高可用

### Q21　Redo Log、Undo Log、Binlog 的区别　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 这题我从层级、作用、写入方式三个维度对比，比单独背定义清楚。
>
> 层级上：Redo Log 和 Undo Log 都是 InnoDB 引擎层的，Binlog 是 Server 层的——这点很重要，意味着 Binlog 对所有引擎都有效。
>
> 作用上：Redo Log 用于崩溃恢复，保证持久性，记录的是物理修改，比如"某页某位置改成什么值"；Undo Log 用于回滚和 MVCC 版本链，是逻辑日志；Binlog 用于主从复制、时间点恢复和归档，记录 DDL 和 DML 的逻辑操作。
>
> 写入方式上有个高频追问：为什么 Redo 循环写、Binlog 追加写？因为 Redo 只需要保留还没刷盘的修改，脏页刷到磁盘后这段日志就可以覆盖了，所以空间固定循环用；而 Binlog 是完整历史，主从复制和时间点恢复都可能用到任意一段，必须追加保留，定期清理。
>
> 三个词收尾：Redo 管持久、Undo 管回滚、Binlog 管复制。

**答题骨架**

| 日志 | 层级 | 作用 | 写入方式 |
|---|---|---|---|
| **Redo Log** | InnoDB | 崩溃恢复，保证持久性 | 循环写 |
| **Undo Log** | InnoDB | 回滚 + MVCC 版本链 | 逻辑上按事务组织 |
| **Binlog** | Server 层 | 主从复制、时间点恢复、归档 | 追加写 |

**追问**：Redo 循环写而 Binlog 追加写？——Redo 只需保留未刷盘的修改，脏页刷盘后可覆盖；Binlog 需完整历史，必须追加。

### Q22　两阶段提交（Redo 与 Binlog 的一致性）　🔥🔥

**答题骨架**

事务提交时：Redo Log 先进入 `prepare` → Binlog 写入 → Redo 再 `commit`。

崩溃恢复时：若 Redo 已 prepare 且 Binlog 完整，则提交；否则回滚。

**目的**：避免主库与从库/备份因两份日志不一致而分叉。

## 七、架构扩展与缓存一致性

### Q23　分库分表后会带来哪些问题？　🔥🔥

**答题骨架**

| 问题 | 方案 |
|---|---|
| 事务一致性（单机事务失效） | Seata（AT/TCC/Saga）或最终一致性 |
| 全局唯一 ID（自增跨库重复） | 雪花算法 / 号段模式 |
| 跨库 JOIN / 分页 / 排序 | 广播表、绑定表、ES 二次聚合 |
| 数据迁移与扩容 | 双写 + 逐步迁移 |

### Q24　缓存与数据库一致性　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 我先给结论：首选**先更新数据库，再删除缓存**，也就是 Cache-Aside。前提是接受最终一致，强一致要上分布式事务，代价太大。
>
> 为什么不选"先删缓存再更库"？因为并发读可能在删完缓存、还没更新数据库的这个空档，把旧值又写回缓存——读线程查缓存没命中，去 DB 读到旧值，回填缓存，结果库更新了、缓存却留着旧值。而"先更库再删缓存"的顺序，这个交错窗口小得多。
>
> 进阶可以聊延迟双删：更新完库删一次缓存，延迟几百毫秒再删一次，用来覆盖那段时间里并发读回填的旧值。更彻底的做法是订阅 Binlog（比如 Canal）异步失效缓存，失败重试兜底。
>
> 最后我一定会主动收一句：这些方案本质都是**最终一致性**，不存在无代价的完美方案——延迟时间难精确、删除可能失败，面试官要的就是你承认这个边界，而不是吹某个银弹。

**答题骨架**

- 首选**先更新数据库，再删除缓存（Cache-Aside）**。
- 不选"先删缓存再更库"：并发读可能在删缓存后、更库前把旧值写回缓存。
- 进阶：**延迟双删**（更库后删缓存，延迟数百毫秒再删一次）；强一致场景用分布式锁或订阅 Binlog（Canal）异步失效。
- **本质是最终一致性**，无完美的无代价方案。

> 与 Redis 笔记 Q7 联动，那里展开了「删除 vs 更新缓存」的完整论证。

### Q25　缓存穿透、击穿、雪崩　🔥🔥🔥

> **🎙️ 90 秒口述版**
>
> 这三个我先用一句话把定义钉死，因为穿透和击穿最容易混。穿透是查**根本不存在**的数据，缓存和 DB 都没有；击穿是**单个热点 key** 过期那一瞬，大量并发打 DB；雪崩是**大量 key 同时过期**或 Redis 整体宕机。
>
> 对应方案。穿透：布隆过滤器提前拦截，或者缓存空值加短过期。击穿：互斥锁重建、逻辑过期、热点 key 永不过期三选一。雪崩：过期时间加随机偏移打散，加高可用集群，再配降级限流。
>
> 区分的口诀我这么记：穿透是"数据本就不存在"，击穿是"数据存在但缓存恰好那一刻没了"，雪崩是"批量一起失效或服务挂了"。面试官如果追线上案例，我会讲清当时的场景、止血动作和事后复盘——这部分背不下来就准备一个自己能讲完整的真实案例。

**答题骨架**

- **穿透**：查不存在的数据，缓存和 DB 都没有 → 缓存空值 / 布隆过滤器。
- **击穿**：热点 key 过期瞬间大量请求打到 DB → 互斥重建 / 逻辑过期 / 热点永不过期。
- **雪崩**：大量 key 同时过期或 Redis 宕机 → 过期时间加随机偏移 + 高可用集群 + 降级限流。

> 与 Redis 笔记 Q6 联动，那里有完整的踩分点与线上止血追问。

## 附：面试答题的三层节奏与复习建议

面试官通常按「**会不会用 → 知不知道为什么 → 出问题怎么办**」三层递进。复习精力建议 **3:4:3** 分配：

- **基础层（30%）**：引擎、字段类型、范式，保持手感即可。
- **原理层（40%）**：B+树、MVCC、锁，花最多时间——这是追问链的主干，也是口述版覆盖最密的地方。
- **故障层（30%）**：至少准备 2–3 个能讲完整的真实案例（慢查询、死锁、缓存雪崩各一）。

**几个容易被追问卡住的点，提前备一句接得住的话**

- 索引为什么 B+树 → 一定要说"非叶子不存数据 → 树矮 → IO 少"，别只说"因为快"。
- RR 的幻读 → 区分快照读和当前读，承认"部分避免"比硬说"完全解决"更稳。
- 间隙锁 → 点出"RR 下防插入，RC 下基本不生效"，并关联死锁概率。
- 缓存一致性 → 先说"先更库再删缓存"，再补"延迟双删 / Binlog 异步"，最后承认是最终一致性。

> **背书口诀**：别逐字背口述稿，记住每道题表格里的「骨架关键词」，考场上用关键词把三层逻辑展开。
> 关键词连成了线，答案自然就顺出来了——这才是"背得下来"的方法。
