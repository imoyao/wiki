## 一、架构设计类（AI最难替代）

### 题目1：设计一个支持10万并发的限流系统

**面试官：** 如果让你设计一个支持10万用户并发的API限流系统，你会怎么做？

**普通回答（AI水平）：**
> "用Redis计数，超过限制就返回429。"

**你的回答（展现架构思维）：**

```
"我会设计一个三级限流体系：

┌─────────────────────────────────────────┐
│ 第一层：全局限流                          │
│ - 限制：10000请求/分钟                    │
│ - 目的：保护系统整体容量                    │
│ - 实现：Redis滑动窗口计数                  │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│ 第二层：IP级限流                          │
│ - 限制：100请求/分钟，突发20               │
│ - 目的：防止单IP恶意攻击                    │
│ - 实现：Redis + 令牌桶算法                 │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│ 第三层：用户级限流                        │
│ - 限制：60请求/分钟，突发10                │
│ - 目的：防止单用户过度使用                  │
│ - 实现：Redis滑动窗口                      │
└─────────────────────────────────────────┘

关键设计决策：
1. 为什么三级？单一限流粒度不够，需要分层防护
2. 为什么滑动窗口？比固定窗口平滑，避免边界突发
3. 为什么Redis？分布式环境下共享计数器
4. 降级策略：Redis故障时允许请求，保证可用性

这套架构在我们项目中支撑了10万用户，
大促期间系统零故障。"
```

**展现的价值：**
- 系统思维：分层防护、降级策略
- 技术选型：算法选择、存储选型
- 工程经验：实际验证的架构

### 题目2：如何处理长对话的Token爆炸问题

**面试官：** AI对话中，历史消息太多导致Token超限，你怎么解决？

**普通回答（AI水平）：**
> "只保留最近10条消息。"

**你的回答（展现深度思考）：**

```
"我设计了5种上下文策略，根据场景动态选择：

策略1：滑动窗口（短对话）
- 保留最近N条消息
- 简单直接，但丢失早期信息

策略2：Token预算（精确控制）
- 按Token数量动态裁剪
- 优先保留近期消息

策略3：摘要策略（长对话）
- 早期对话生成摘要（200Token）
- 保留近期完整消息（1000Token）
- 从4000Token降到1200Token

策略4：语义检索（跨话题）
- 检索与当前问题相关的历史
- 而非简单按时间裁剪

策略5：混合策略（智能选择）
- 消息数>20 → 用摘要策略
- Token>4000 → 用Token预算
- 默认 → 滑动窗口

实现细节：
- 摘要生成：调用LLM提取主题、关键点、实体
- 触发条件：消息数>10且Token>3000
- 增量更新：避免重复生成摘要

效果：支持100轮+流畅对话，Token成本降低60%。"
```

**展现的价值：**
- 算法设计：多策略组合
- 成本控制：Token优化
- 用户体验：长对话不"失忆"

## 二、复杂问题解决类（AI无法替代）

### 题目3：线上服务突然变慢，如何排查

**面试官：** 生产环境API响应从1秒变成10秒，你怎么排查？

**普通回答（AI水平）：**
> "看日志，找错误，优化代码。"

**你的回答（展现排查能力）：**

```
"我会按这个流程排查：

第一步：确认现象（2分钟）
- 看监控：是所有接口慢还是某个接口？
- 看时间：什么时候开始的？是否有发布？
- 看范围：所有用户还是部分用户？

第二步：定位层级（5分钟）
┌─────────┐ 应用层：CPU、内存、GC
│  应用    │ → 线程Dump分析
├─────────┤
│  依赖    │ 中间件：Redis、MySQL、MQ
│  服务    │ → 连接池、慢查询
├─────────┤
│  下游    │ 外部：LLM API、第三方服务
│  服务    │ → 熔断器状态、响应时间
└─────────┘

第三步：深度分析（10分钟）
- 如果是数据库慢：
  - 看慢查询日志
  - 分析执行计划
  - 检查索引、锁竞争
  
- 如果是LLM API慢：
  - 检查API Key轮询是否正常
  - 看是否有单Key限流
  - 考虑切换备用供应商
  
- 如果是代码问题：
  - 火焰图分析热点
  - 检查是否有死循环
  - 内存泄漏分析

第四步：应急恢复（并行）
- 降级：关闭非核心功能
- 限流：收紧限流阈值
- 扩容：临时加机器
- 回滚：如有发布立即回滚

第五步：根因解决
- 修复代码/配置问题
- 增加监控告警
- 写复盘文档

实际案例：
上次我们遇到类似问题，
发现是Redis连接池耗尽导致。
原因是新功能没正确释放连接，
10分钟定位，5分钟修复。"
```

**展现的价值：**
- 系统化思维：分层排查
- 应急能力：快速恢复
- 工程经验：实际案例

## 三、技术选型类（需要经验判断）

### 题目5：限流算法选哪个

**面试官：** 限流用滑动窗口还是令牌桶？为什么？

**普通回答（AI水平）：**
> "令牌桶好，可以应对突发流量。"

**你的回答（展现技术判断力）：**

```
"我根据场景组合使用：

算法对比：
| 算法 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 固定窗口 | 简单 | 边界突发 | 简单限流 |
| 滑动窗口 | 平滑 | 内存大 | 精确限流 |
| 令牌桶 | 允许突发 | 实现复杂 | API限流 |
| 漏桶 | 流量整形 | 无突发 | 严格限速 |

我的选择：

1. 中间件层（HTTP限流）→ 滑动窗口
   - 原因：分布式环境，需要精确计数
   - 实现：Redis + 滑动窗口
   - 场景：全局/IP/用户三级限流

2. 服务层（API限流）→ 令牌桶
   - 原因：单机精确QPS控制，允许突发
   - 实现：内存令牌桶
   - 场景：LLM API调用限流

3. 对话层（消息限流）→ 多级滑动窗口
   - 原因：需要分钟/小时/天多级限制
   - 实现：Redis多Key计数
   - 场景：防刷屏

关键决策因素：
- 分布式 vs 单机
- 精确性 vs 允许突发
- 实现复杂度
- 运维成本

实际效果：
这套组合支撑了10万用户并发，
大促期间精准限流，系统零过载。"
```

**展现的价值：**
- 技术深度：算法理解
- 选型能力：场景匹配
- 系统思维：组合使用

## 四、业务理解类（AI最难替代）

**面试官：** 客户说"我要一个AI客服"，你会怎么做？

**普通回答（AI水平）：**
> "用RAG技术，接入知识库，做问答系统。"

**你的回答（展现业务思维）：**

```
"我不会直接开始写代码，而是先问清楚：

第一步：需求挖掘（1小时）
- 现在客服团队多少人？月薪多少？
- 每天咨询量多少？集中在什么时段？
- 客户主要问什么问题？重复度多高？
- 现有解决方案是什么？痛点在哪？
- 预算多少？期望什么时候上线？

第二步：场景分析
假设客户说：
- 3个客服，月薪5000，每天300咨询
- 80%是重复问题（价格、物流、售后）
- 夜班没人，客户抱怨响应慢
- 预算5万，希望1个月上线

第三步：方案设计
┌─────────────────────────────────────────┐
│ 核心目标：替代2个人工，夜班自动响应        │
├─────────────────────────────────────────┤
│ 技术方案：                                │
│ 1. RAG知识库：产品FAQ、售后政策          │
│ 2. 多轮对话：理解上下文，追问澄清         │
│ 3. 工具调用：查订单状态、物流信息         │
│ 4. 人机协作：复杂问题转人工              │
├─────────────────────────────────────────┤
│ 接入渠道：微信公众号（客户主要渠道）       │
├─────────────────────────────────────────┤
│ 效果预期：                                │
│ - 自动回答率：80%                        │
│ - 响应时间：从5分钟降到5秒               │
│ - 年度节省：12万人工成本                 │
│ - ROI：投入5万，节省12万，2.4倍          │
└─────────────────────────────────────────┘

第四步：风险评估
- 知识库建设需要客户配合
- 初期需要人工审核AI回答
- 复杂问题处理需要人工兜底

第五步：实施计划
- Week 1：需求确认、知识库梳理
- Week 2：系统部署、知识库录入
- Week 3：测试优化、人工审核
- Week 4：正式上线、培训交接

关键成功因素：
不是技术多先进，而是客户配合度、
知识库质量、持续优化迭代。"
```

**展现的价值：**
- 业务理解：挖掘真实需求
- 方案设计：技术+业务结合
- 价值量化：ROI计算
- 项目管理：实施计划

## 五、总结：如何展现价值

### 回答结构模板

```
1. 背景分析（展现系统思维）
   "这个问题需要考虑...几个方面"

2. 方案对比（展现技术判断力）
   "我评估了N个方案，各自的优缺点..."

3. 决策逻辑（展现经验）
   "我选择X方案，因为..."

4. 实现细节（展现工程能力）
   "具体实现上，我设计了..."

5. 效果验证（展现实战经验）
   "实际运行效果..."
```

### 与AI的区别

| 维度 | AI能做到 | 你能做到 |
|------|----------|----------|
| 知识 | 列举方案 | 结合场景选择最优 |
| 经验 | 通用建议 | 踩坑后的具体决策 |
| 思维 | 单点回答 | 系统化架构设计 |
| 业务 | 技术实现 | 需求挖掘、价值量化 |
| 风险 | 理想情况 | 实际约束、降级策略 |

### 一句话总结

> **"AI能给出正确答案，但给不出在约束条件下的最优解。**
