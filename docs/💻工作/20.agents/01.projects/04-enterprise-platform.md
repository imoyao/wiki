## 二、完整叙述（主简历已压缩，此处为原稿）

- **业务背景**：无代码集成平台（iPaaS），第三方应用以「连接器」接入，用户在画布上拖节点编排流程。平台同时解决两件事：异构系统在参数 / 凭据 / 字段语义上表现一致（连接器层），以及「哪些动作收费、收多少、怎么扣、扣完还能不能用」（计费履约层）。

- **核心难点**：

  1. **参数不是静态表单**——多级动态依赖（base → table → record），下一层候选值要拿租户凭据实时调第三方接口才算得出，且层数不固定。
  2. **没有统一注册入口就退化成复制粘贴**——339 个连接器各写一套凭据校验 / 连通性测试 / 字段映射，新增接入成本随数量线性上升。
  3. **售卖形态不止一种**——6 类计费模式（周期 / 费率 / 包次 / 包时 / 扣费字段 / 余额抵扣）必须共用一套扣减与校验，否则每加一种卖法就要改一遍执行链路。
  4. **卖掉了再改规则**——套餐模板（价格、额度）与履约实例（已售出的包、已用掉的量）必须分离，否则改价会动摇存量用户；升级时已用量还不能重置，否则「先把额度刷光再升级」等于白拿一份新额度。
  5. **同一份额度被多个租户共享**——集团客户让子公司共用主企业买的包：不复制额度、只授予可见性，扣减按优先级排序，查询还要防自有包与共享包重复计数。

- **核心工作**：

  - **连接器层**：参数契约单一来源（类型 / 必填 / 可选值 / 复合类型 / 动态级联，渲染、校验、执行读同一份定义，新增动作只写声明不写渲染代码）+ 能力自注册表（凭据校验 / 连通性 / 字段映射 / 样例数据四类入口）；把 LLM 封装成连接器动作（模型名作 enum、分类目标用「字段名 + 自然语言描述」）；兜底三层（重试 3 次 → 落对账表补偿而非静默丢弃 → 多 Key 池轮换剔除失效 Key）；失败一律不中断流程——权限或额度不足时把动作入参降级成一条可读提示回给编排侧，不抛异常打断。
  - **计费模型**：按「指标字典 → 套餐模板 → 履约实例 → 账本流水」四层拆分；计费点收敛为 6 类模式，前一类卖套餐、后五类卖动作（单次费率 / 次数包 / 时长包 / 按第三方返回用量扣 / 余额抵扣）；指标用 `switch / counter / rate / basic` 四类语义 + `count / sum / max` 三种聚合方式描述，一份模型同时表达「额度上限」与「并发限速」。
  - **交易策略**：开通 / 续费 / 升级**抽象为策略模式**（三种交易各一个实现，按 `trade_type` 分派），统一契约 `validate → quote → fulfill`；同一策略对象既报价又履约，报价口径与结算共用一份规则——结构上让支付回调可反算对账。三条路径的差异收敛在各自的策略里：开通继承免费版已用量、续费原地延期（一个包对 N 个订单、不新建）、升级合并功能点换包（额度取新、已用取旧、到期日不变）。升级补款的公式随售卖周期演进：`(新价−原价)/365 × 剩余天数` → `(新价/新周期天数 − 原价/原周期天数) × 剩余天数`，动因是引入月付后分母写死 365 失效。
  - **校验与扣减**：业务侧零计费逻辑，动作执行前调权限与余额两个接口（预付费传预计金额、仅验开通则不传）；扣减按「资源包额度 → 按单价折现金余额 → 余额不足拒绝」三级降级，额度耗尽自动转按量付费、不中断执行。多包并存时按指标聚合方式合并（`count/sum` 求和、`max` 取最大），权限判定上额度型任一包可用即放行、速率型取最严——额度可叠加而速率共享同一物理上限，这个不对称是有意设计；主控指标一票否决，一把关掉整包其余指标；付费状态与权限中台联动，激活授予角色与资源权限、禁用回收。扣减不走「读—改—写」，交给数据库侧原子加减配合行锁，结构上扣不成负数；余额告警只在跨过阈值那一刻发一次，不重复刷屏。

- **项目成果**：接入层支撑 **339 个连接器**（327 个含动作定义），同一套契约覆盖渲染、校验与执行；**6 类计费模式**覆盖按期与按次两种售卖，计费履约独立成服务（支付 / 钱包 / 插件三组 API）；该契约设计在 2023 年后迁移为 Agent 工具层——9 个工具 schema 的字段约束、归属字段服务端覆盖、「工具描述就是 prompt」的取舍，源头在此。

- **边界**：当时无 Function Calling，与今日 tool schema 是**结构同构而非直接移植**；动态依赖参数在 Agent 场景下尚无解；交易策略以 `trade_type` 为分派键，新增售卖形态需扩展策略族；升级差价按日均价折算，未处理跨版本赠送额度的部分退费；计费内核在两个仓库各存一份拷贝且已开始漂移，本质是缺一个共享内核包。

## 三、主简历压缩版（6 条）

- **参数契约单一来源**：把动作抽象成参数契约（类型 / 必填 / 可选值 / 复合类型 / 多级动态级联），界面渲染、提交校验与执行取参读同一份定义，新增动作只写声明不写渲染代码；**339 个连接器**（327 含动作定义）以同一套契约接入。
- **能力自注册表**：连接器自注册凭据校验 / 连通性测试 / 字段映射 / 样例数据四类入口，替代「每个连接器各写一套」的复制粘贴——**没有统一注册入口，接入成本随数量线性上升**。
- **计费模型四层拆分**：指标字典 → 套餐模板 → 履约实例 → 账本流水；模板层（价格、额度）与实例层（已售出的包、已用掉的量）分离，**改价不动存量用户**。计费点收敛为 6 类（周期 / 费率 / 包次 / 包时 / 扣费字段 / 余额抵扣），一份模型同时表达「额度上限」与「并发限速」。
- **交易收敛为策略族**：开通 / 续费 / 升级各一个实现，统一 `validate → quote → fulfill` 契约，同一对象既报价又履约——**报价口径与结算共用一份规则，结构上让支付回调可反算对账**。升级的关键规则是「额度取新、已用取旧」，堵住「先刷光再升级」白拿额度的漏洞。
- **校验前置 + 三级降级**：业务侧零计费逻辑，动作执行前只调权限与余额两个接口；扣减按「资源包额度 → 按单价折现金余额 → 余额不足拒绝」降级，额度耗尽自动转按量付费、**不中断执行**；多包按指标聚合方式合并（`count/sum` 求和、`max` 取最大），额度型任一包可用即放行、速率型取最严。
- **失败不打断流程**：权限或额度不足时把动作入参降级成一条可读提示回给编排侧，不抛异常中断——**这是今天 Agent 工具层「tool error 转文本回给模型」的同一条原则，只是当年消费方是流程图**。

## 四、面试追问预案（深度问答见 `../payment-architecture.md` §7 的 14 问）

**Q1：这项目跟 Agent 有什么关系？**
> 是工具层的前身。当年工具的使用者是「用户画的流程图」，今天是「模型的决策」——**变的只有调用方**。参数契约、凭据管理、失败补偿、执行前校验，这四件事一个没变。所以我在 Agent 项目里对工具 schema 的判断，源头在这里。

**Q2：为什么说「结构同构」而不是「直接移植」？**
> 因为当年没有 Function Calling。模型只是流程里的一个节点，不参与「调什么、按什么顺序调」的决策。所以参数必须由人在配置阶段填全，平台没有「运行时发现能力」这一层。今天 tool schema 是给模型看的、要能被模型理解并自主填，这两件事在**约束来源**上完全不同——我只是说结构像，不是说当年就做对了。

**Q3：6 类计费模式为什么要统一？**
> 因为不统一的话，每加一种卖法就要改一遍执行链路。而且更糟的是**校验和扣减会分叉**——一种卖法在入口校验、另一种在执行后补扣，用户体感就是「有时候能用有时候不能用」。所以先抽「指标」这个原子概念，6 种模式都表达成指标的额度和聚合方式，扣减只有一条路。

**Q4：升级「额度取新、已用取旧」具体怎么实现？**
> pandas `combine_first`：以新包的 `bind_value` 为底，用旧包的 `usage` 覆盖。一行代码，但业务含义很重——**只重置额度、不重置已用量**。否则用户先在低版本把额度刷光、再花小钱升级，等于白拿一份新额度。开通时继承免费版 usage 是同一个漏洞的另一种封堵。

**Q5：策略模式是真做了还是设计？**
> 是设计，代码现状是按 `trade_type` 在四个地方各写了一遍 if/elif：下单算价、二次支付算价、回调履约，外加 `upgrade_rule` 两个仓库各一版。**这不是为了写设计模式而设计，是代码里已经躺着 4 份拷贝**——算价有两份，结构上就不知道以哪份为准，所以现在做不到对账。抽成策略后能。`payment-architecture.md` §4 有可直接落地的伪代码。

**Q6：付费校验前置为什么是两跳？**
> 第一跳查权限（额度还有没有）、第二跳查余额（钱够不够）。看起来能合并，但不能：一个是「开通没开通」，一个是「这次的钱够不够」。业务侧不持有任何计费规则，只按接口返回决定继不继续——**这是整套系统解耦最干净的一层**。

**Q7：这个项目最弱的地方？**
> 三个：① 交易策略没抽出来，公式还并存两版；② 建包与订单关联没有事务，靠手工补偿；③ 计费内核在两个仓库各存一份拷贝、已经开始漂移，本质是缺一个共享内核包。前两条是架构问题，第三条是组织问题。
